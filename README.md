# twake-harness

The Twake Space agent harness: one shared service, written in TypeScript, that gives every user of a Twake Workplace platform a personal assistant in Twake Chat, and gives the organization an analysis agent.

- Isolation between users is enforced in code and in the database, not by separate pods.
- Assistants are created by their owner from Twake Chat, through a creator conversation, with nothing to configure.
- Each assistant has memory, skills and self-learning, and acts in the applications with its owner's rights, through the platform's API gateway, asking before it acts.
- The service reaches the outside world only through APISIX, keeps the assistants' encryption secrets in the platform's OpenBao, and logs every action with its metadata at `info`, the conversation itself (prompt, answer, reasoning, tool arguments and results) only at `debug`, so the messages it decrypts stay out of production logs.

## Stack and conventions

Aligned with `twake-workplace-common-settings` wherever it has an opinion: TypeScript in strict mode as ES modules, npm, Vitest, Drizzle with postgres.js, zod, ESLint flat config and Prettier with tabs. The HTTP layer is Fastify: common-settings is a SvelteKit application and carries no backend framework, Fastify is the server already used in Twake backends, and its pino logger writes the JSON lines with a request id that the spec requires. Node 22.

Code follows the Twake JavaScript and TypeScript conventions: named exports only, explicit types on exported symbols, `unknown` for external data, no enums, `#` for private members, comments only for business reasons.

## Roles

One image, one role per deployment, chosen by `HARNESS_ROLE`:

- `api` serves the HTTP API behind APISIX.
- `worker` runs the daily curation: for every owner, under their own principal, it merges duplicate memory entries and turns a request made the same way in three conversations or more into a skill proposal for that owner. It serves its health check and its metrics, and nothing else.
- `matrix` is the Matrix application service: it receives what Synapse pushes, answers as the creator user and the assistants, and calls Synapse through the `matrix` route of APISIX. `npm run matrix:registration` prints the registration file Synapse loads, given `MATRIX_APPSERVICE_URL`, the APISIX route Synapse pushes to.

The Matrix tests start a real Synapse in a container, so Docker is needed to run them.

### Behind the gateway

The api role is meant to sit behind APISIX only. With `GATEWAY_SHARED_SECRET` set, every request of the API must carry that value in `x-twake-gateway`, which the gateway injects on what it forwards; anything else gets a 403 before any identity work, while the health check and the metrics stay open to the cluster. The gateway writes the audit record of every contract call, one per call (agent, user, contract, method, path, status); the harness forwards the correlation id of the turn in `x-correlation-id`, so the record links back to it, and posts no record of its own.

### Replaying against dev

`npm run test:dev` replays the prototype's black-box checks (identity, default rights, memory and session isolation, identity override, two users at once) against a deployed harness through its gateway, with no database or container: set `HARNESS_BASE_URL` to the api route (for instance `https://apisix.dev.twake.lin-saas.com/agents`) and `HARNESS_TOKEN_A` and `HARNESS_TOKEN_B` to the access tokens of two users carrying the `twake-harness` audience. The results land in `dev-results/vitest.json`, to keep with the pilot. Without those variables the suite is skipped.

### Jobs between roles

The roles hand work to each other through the `jobs` table: a Matrix message becomes a `turn` for the api role, its answer a `send` for the matrix role, and each action of the turn a `progress`, which the matrix role shows its owner while the turn works: the counts of a room have a group of their own, so that none holds an answer back, even when no matrix role takes them, as during a rollout. Any replica claims any job (`for update skip locked`), so the api role scales horizontally; the chart ships a horizontal autoscaler for it (`autoscaling.enabled`), never below one replica. A job carries a dedup key, so an event Synapse delivers twice makes one turn, and a group key: the turns of one owner and the answers of one room run one at a time, in the order they were queued, whichever replica takes them. A job still running after its lease (fifteen minutes) is handed back to the queue, as its replica is taken for gone.

### While a turn works

The owner sees their assistant at work on a message, or on the yes that resumes a turn: eyes (👀) on it and the assistant typing, then a check mark (✅) once it is answered. A turn that has not answered after `TURN_STATUS_DELAY_MS` also posts a status message, "⏳ On it…" in the owner's language, as a reply to that message and encrypted like every other, which then counts the actions the turn has done, "⏳ On it… (3 actions done)", in edits at least that delay apart. The answer, or the notice of a failed or refused turn, then goes out as a message of its own, as it always did, and the status closes on "✅ Done", "⏸️ Limit reached" when the turn stopped at its limit of tool calls, or "❌ Not done" after a notice, as an edit (`m.replace`) that Twake Chat marks as edited: Synapse's default push rules notify nobody of an edit (`.m.rule.suppress_edits`), and the owner is to be notified of what came of their message. A turn that ends on a question to its owner keeps the question a message of its own, which they answer in their next message, and the status then tells them to answer below. A status never outlives its turn: with no reply ready five minutes after the message, as long as the typing lasts, or none gone out five minutes after it was ready, or when the matrix role stops, it says that this takes longer than expected, and an answer that comes later goes out as a message of its own.

### Admission

A turn is admitted before any model call. The turns per minute of a user, those of the whole harness and the daily tokens of a user are counted in the database, so the limits hold whatever the number of replicas; the turns in flight, the queue of a full replica and the slots a user holds in it are each replica's own, as are the counters of `/metrics`. A refused turn gets a 429 with its reason.

The limits are the `ADMISSION_*` variables of the configuration. The chart sets each one from its `config.admission*` value (`admissionMaxInflight`, `admissionUserQueue`, `admissionUserPerMinute`, `admissionUserDailyTokens`, `admissionGlobalPerMinute`) only when that value is set, as a whole number. One turn that calls several contracts can use tens of thousands of tokens, since every model call sends the conversation again, so a deployment where people test often may need a larger daily budget per user.

### Encryption

The assistants' rooms are created encrypted and every message in them is encrypted end to end. The matrix role holds one encryption store per assistant on its volume, acts as each assistant's device through the application service (device masquerading, MSC3202), and receives the key shares Synapse pushes with the transactions (MSC2409), so no assistant runs a sync loop. Both flags are enabled on the Synapse the harness is registered with. The fallback, had push proved unworkable, would have been one sync loop per assistant; it was not needed. An assistant's encryption state is prepared when the role starts and when it is invited, so a key share that arrives while the role was away is not lost: Synapse redelivers the transaction and the message is answered once the role is back.

In an encrypted room, an assistant, the organization agent included, takes a turn only from a message that reached its device encrypted: one in the name of the owner, or of a member, that came in clear was written on the server side, by a component or by anyone holding their token, and starts nothing; the matrix role logs it. A room is encrypted when the assistant's encryption store says so: the SDK reads the room's `m.room.encryption` state and keeps it, since encryption is never turned off, and encrypts the assistant's own messages by it. The SDK takes a state it failed to read for no encryption, so a room it does not hold as encrypted is read again before a message in clear is heard: only the homeserver's answer that the room has no such state makes the room clear, and a room whose state cannot be read, the homeserver failing or refusing to answer, counts as encrypted, the message being logged with that reason. A room opened without encryption, as a member may open one with the organization agent, is heard as before.

Every assistant device is signed by the assistant's own cross-signing identity, which the harness holds whether the escrow is on or not: Twake Chat sends the room keys only to the devices that the owner of a cross-signing identity signed, so an unsigned device never reads its owner's messages. The identity is created when the assistant first speaks, or at once when a provisioner asks for the assistant (see Provisioning API). An identity on the assistant's Matrix user that the harness does not hold, such as one another application left there, is replaced, and so is the harness's own when its store is lost and no escrow keeps it. The cross-signing keys go up as the application service, which Synapse lets replace an identity without interactive authentication; the device's own token could not. The database keeps the master public key the harness holds, to tell its identity from any other.

### The owner's sessions

An assistant takes its owner's words, a message that starts a turn or answers a question of the harness, or a reaction that answers one, only from a session of theirs that their cross-signing identity signed, and only from the identity it holds for them: the first one it saw published for them, kept in the database. The matrix role decrypts the event again with the assistant's own encryption engine, which tells the device the room key came from, queries the owner's keys as the homeserver publishes them, and checks every signature itself: the device's own, the self-signing key's on the device, the master key's on the self-signing key. A session that no identity of the owner signed, or that another identity than the one held signed, does not count as theirs. Twake Chat sets an identity up at the first sign-in and signs every later session with it, from the recovery key it keeps for its user.

`OWNER_DEVICE_TRUST` says what becomes of the words of another session. With `enforce`, nothing comes of them: no turn, no answer, a call waiting for the owner still waits; the matrix role logs the session, never the words, and the assistant tells the owner in their language, at most once a minute per session, why and what to do: verify that session from another one in Twake Chat (Settings > Devices, Verify), sign in to Twake Chat again when their account has no identity at all, or accept their new identity (below). A check that cannot be made, the homeserver failing to answer, takes nothing either, and the owner is told to try again. Words that came in clear, in a room of the assistant that reads as clear, take nothing either, and the owner is told why; `report` takes them as before, and logs them. With `report`, the default, the words count as before, while the matrix role logs, for every message of an owner, the session it came from, whether their identity signed it and whether that identity is the one held, and the assistant tells the owner once per session that it is not verified, and how to verify it. The identity is held in either mode. Encrypted words count once: the same ones under another event, a copy, start nothing in either mode, and the matrix role logs them; it remembers what it received for thirty days. The creator conversation takes an owner's commands under the same rule and the same setting: with `enforce`, a command takes effect only when it came encrypted, from a session their identity signed, and the owner is told why when it did not; with `report`, every command takes effect as before, and the creator logs and tells the owner as the assistants do. The organization agent, which acts for no owner, hears its members as before.

An owner who resets their identity, so that their sessions are signed by a new one, has their words refused, or reported, until they accept the new identity through the API, with their own token and the `chat` right; no message in the chat can. `GET /v1/assistants/me/owner-identity` answers with the identity held, `pinned` (its master key, `pinned_by` `first_use` or `api`, and `pinned_at`), and with the identity that signed the session their words last came from, when it was another one, `published` (its master key and `seen_at`), null otherwise. `PUT /v1/assistants/me/owner-identity` with `{ "master_key": "..." }`, the key `published` shows, makes that identity the one held (200); any other key gets a 409 with both. Both work for an owner who has no assistant yet, whose commands the creator takes under the same rule.

### Identity

One person is one principal everywhere in the harness: the subject of their platform token, which is their email. A user of the homeserver is that same person: `@alice:<MATRIX_SERVER_NAME>` is the principal `alice@<MATRIX_MAIL_DOMAIN>`, and the mail domain defaults to the server name. The creator conversation, the API, the `owner` of the events the dispatcher posts and the owner header of the contract calls all carry that principal, so the assistant created from Twake Chat is the one the API returns for the owner's token, and a delegation keyed by email at the gateway matches. A principal of another mail domain has no account on the homeserver, so no room can be opened for it: the API refuses to create its assistant with a 422.

### Organization agent

With `ORG_AGENT_ENABLED`, the matrix role runs one more bot, the organization agent: a Matrix user in the assistants' namespace (`ORG_AGENT_LOCALPART`), with its own name and persona, that joins the direct messages of the members named in `ORG_AGENT_MEMBERS` and nobody else, greets them, and answers each of them with the member's identifier in front of the message. It acts under the organization principal, `org`, so its memory is the organization's and its skills library is the organization's; no token can carry that subject. Its contract calls carry no owner header: the gateway sees the harness key alone.

### Events

The dispatcher wakes an assistant by posting an event to `POST /v1/events` with the owner's identifier, the event's id and its type, under a token of one of the service clients named in `EVENTS_CLIENT_IDS` (by subject); a user's token is refused. The harness queues a turn in the owner's room, deduplicated on the event id, in which the assistant reads the event through the contracts and tells the owner; whatever that turn prepares to write waits for the owner's yes (see Consent). An invitation is read, and its slot checked in the owner's calendar, by the harness before the model speaks: the model tells the owner who invites them, to what, when, and whether they are free, and prepares the acceptance, which the harness then asks them about under the model's words. An event for a user without an assistant is refused and logged.

### Provisioning API

A client of the homeserver may give its user their assistant without the creator conversation: it asks a provisioner it trusts, such as the identity server it already authenticates its users with, which calls the harness on the user's behalf. The provisioner authenticates with an access token of its own OIDC client (client credentials grant, audience `AUTH_AUDIENCE`), and only the clients named in `PROVISIONER_CLIENT_IDS` (by subject) are admitted: no token or an invalid one gets a 401 `{"error":"invalid token"}`, a valid token of anyone else a 403 `{"error":"not a provisioner"}`. Behind the gateway, the shared secret is required as on the rest of `/v1`. The owner is named by their Matrix identifier, URL-encoded in the path; one that is not a user of this homeserver gets a 422 `{"error":"owner not on the homeserver"}`.

`PUT /v1/provisioning/assistants/{owner}`, with an optional body `{"timezone":"<IANA zone>"}` (the zone the owner's client reports, accepted and not kept: the harness has no zone per owner), gives the owner's assistant:

- `200 {"userId":"@<prefix><localpart>:<server>","deviceId":"<device>","masterKey":"<public key>"}` once the assistant's device is signed by its cross-signing identity. `masterKey` is the public master cross-signing key, unpadded base64, the value in `master_keys[userId].keys` of `/keys/query`: the client checks that the identity the homeserver publishes has this key, then trusts the device on it. The same answer comes back on every later call.
- `503 {"error":"not_ready"}` with `Retry-After: 5` until then. An owner without an assistant gets one at the first call, named from the locale's catalog and without a room of its own, and the matrix role makes its device and its identity at once rather than when it first speaks. That preparation is tried again by the harness itself, with a backoff, until the identity is ready, so the provisioner only needs to ask again; the matrix role also prepares every provisioned assistant at its start, room or not.
- `409 {"error":"recovery_needed"}` while the assistant's escrowed identity waits for its owner's recovery, after the matrix role lost its store: asking again changes nothing until the owner calls `POST /v1/assistants/me/recover` (see Key escrow), after which the assistant's identity comes back, on a new device. A provisioner should not retry this answer, and can tell the owner what to do.
- `502 {"error":"assistant creation failed"}` when the homeserver refused the assistant's account.
- The answer always describes the assistant the provisioner asked for: an identity recorded for an earlier identifier of the owner's assistant, as before a change of the assistants' prefix, is never handed out.

`PUT /v1/provisioning/assistants/{owner}/home`, with `{"roomId":"!room:server"}`, names the direct room the owner's client opened with the assistant: the room the assistant writes to its owner in, as an event's turn does, and one of the rooms it answers them in. `204` once recorded; `404 {"error":"no assistant"}` for an owner without one; `409 {"error":"not a member"}` when the assistant has not joined the room within a few seconds, or the owner is not in it; `409 {"error":"not a direct room"}` when anyone else is in it, since what the assistant writes there would reach them too.

The owner's client opens that room itself and invites the assistant. An assistant joins a room only when its own owner invites it, and the room then becomes one of its rooms, where it answers its owner as in the room it opened; the first such room becomes the room it writes to its owner in, until the provisioner names another. An invitation from anyone else is declined and logged. The creator and the organization agent keep their own rules.

For now an assistant works in direct rooms only, its owner and itself: everyone else in a room would read what it writes its owner, their memory and their applications' data included. Invited by its owner into a room where anyone else is, joined or invited, it declines: it leaves with the reason in the owner's language, and logs it. A room where it answers its owner that someone else comes into, joined or invited, stops being one of its rooms: it says why there, leaves with the same reason, and that room is no longer the one it writes its owner in. A mode for rooms with others, without the owner's memory nor their applications, is to come (#79).

In every room of the assistant (the room it opens itself when its owner creates it, each room its owner invites it to, and the room a provisioner names) the assistant announces the commands it answers itself (MSC4332): the state event `org.matrix.msc4332.commands`, its state key the assistant's id, its content `{"commands":[{"name":"help","syntax":"help","description":{"m.text":[{"body":"..."}]}}]}` with the description in the owner's language, which Twake Chat offers after « / ». The command list lives in `src/matrix/commands.ts`. A room that already holds the same announcement is left as it is; a room that refuses the state event, by its power levels, is logged and tried again only at the next invitation or naming of it. When the owner sends `!help` (as Twake Chat sends an announced command, the command also named in the message's `org.matrix.msc4332.command` content) or `/help`, the harness answers itself, in the owner's language, without a model turn.

### Key escrow

With `ESCROW_ENABLED`, the matrix role escrows each assistant's identity in the platform OpenBao, through the `openbao` route of APISIX and the Kubernetes auth method (`OPENBAO_K8S_ROLE`, the pod's projected token with the audience the chart sets): once an assistant's device is signed by its identity (see Encryption), a key backup is opened on the homeserver, and the secret storage key, the three cross-signing secrets, the backup key and its version go to `<mount>/data/<prefix>/<owner>`. The escrow only stores the keys: the identity itself is the harness's either way, and an identity replaced since is escrowed again. The database keeps the path, the master public key and the backup version only; every read and write of the escrow is logged with the principal. Room keys are backed up as they come and go. After a lost store, the escrowed identity on the homeserver is not replaced: the new device waits, and `POST /v1/assistants/me/recover` (the owner's token) puts it back on the escrowed identity, which the owner's clients already trust, and the backup goes on; the room keys of the lost device stay in the server backup, unreadable until the crypto bindings can import them. At rest, the store on the volume is protected by the volume's own encryption (an encrypted storage class).

### Skills

Skills follow the Agent Skills format: a name, a description and Markdown instructions. Each user has a library, the organization has one, and every skill has exactly one owner. The system prompt lists the skills a user may read, with their descriptions; the model reads one with `scoped_skills_read` when it applies and searches them with `skills_search`. What the assistant learns becomes a proposal through `skills_propose`, invisible to the model until its owner approves it (`POST /v1/skills/proposals/:id/approve`). An administrator, a principal with the `skills.admin` right, writes organization skills (`POST /v1/org/skills`) and promotes a user's proposal into the organization library by copy (`POST /v1/org/skills/promote/:id`), leaving the user's library untouched. Row-level security enforces all of it: a user never sees another user's skill, and the organization's are written by administrators only.

### Session search

The model finds past conversations with `session_search`, by words they contain, among the owner's sessions only; the result gives the session ids and a snippet, and `scoped_sessions_read` opens one.

### Language

Each assistant speaks its owner's language: the one the owner chose by asking their assistant, which calls `set_language`, or else the deployment's (`ASSISTANT_LOCALE`). The model is told, in that language, to speak it, and every fixed sentence the harness says to that owner follows it: the consent questions, the acknowledgements and notices of an answer, the status of a turn that takes a while, the busy and failure notices, and the creator's replies. The choice is stored with the assistant, and kept if the owner creates it again. Changing it takes the `settings.write_own` right, which a turn an event started never holds; the organization agent speaks the deployment's language with every member. Answers to the harness's questions are understood in every language it speaks.

### Contracts as tools

The harness reads the curated OpenAPI that APISIX serves and turns every operation that has an `operationId` into a tool named after it, dots replaced by underscores. A tool call goes to APISIX at the path the document gives, as OpenAPI reads it: the path of its first server, the root when it names none, then the operation's path; a server on another host keeps only its path, with a warning, since the gateway is the harness's only way out, and `CONTRACTS_BASE_PATH`, empty by default, prefixes the calls for a gateway that mounts the contracts elsewhere. It carries the harness consumer key, the contract id and the owner in `x-twake-on-behalf-of`; the gateway attaches the owner's token, so the harness never holds one. What a contract returns is handed to the model as data, status included, and every call is logged; the gateway writes its audit record. The catalog is loaded at start and refreshed on an interval; a failed refresh keeps the previous catalog. A write operation declares in `x-twake-risk` whether it is `low` or `high`; one that declares neither is `high`, so that a forgotten declaration asks its owner each time (see Consent), and so is one that declares anything else, with a warning logged once for its operator. A write whose contract can tell what a call would do without doing it declares `x-twake-preview: true`, and its owner sees that before they confirm the call (see Consent); any other value, and a preview a read declares, is ignored, with a warning logged once.

### Consent

An assistant reads an application only once its owner allowed it, and writes there only once its owner allowed that as well: allowing it to read never lets it write. A contract belongs to the application its id starts with (`mail` for `mail.emails.read.v1`); a `GET` contract reads, and any other method writes. The first time an assistant would read an application, or write in it, at a level its owner never allowed, the harness freezes the call as the model wrote it, stores it for its owner, and ends the turn with its own fixed question in its owner's language: nothing reaches the application but the preview of a write that offers one (see below), and nothing the model or a third party writes can phrase that question. The rights to call and to act through contracts stay above consents: an owner whose assistant may not act is refused a write as before, whatever they allowed. The assistant's own feed of workplace events (`events`) is read without asking, and the organization agent, which acts for no user, never asks. Consents and waiting calls are rows of their owner, under row-level security. The assistants of the pilot kept reading Calendar when consents came, and writing there when writing asked too: every principal that could call contracts then got Calendar read, and every principal that could act through them Calendar write, so that accepting an invitation asks them nothing but whether to accept it.

Either question names the application and says what its level, reading or writing, covers there, in its owner's language, as the catalog describes it: at the root of the OpenAPI document, `x-twake-domains` gives each domain a `name`, and what its `read` and `write` levels cover, in each language the harness speaks (`en`, `fr`), as plain words on one line (at most 64 characters for a name, 200 for what a level covers), addressed to the owner, without a final period:

```json
{
	"x-twake-domains": {
		"mail": {
			"name": { "en": "Twake Mail", "fr": "Twake Mail" },
			"read": {
				"en": "list, search and read your mail",
				"fr": "lister, chercher et lire tes mails"
			},
			"write": {
				"en": "prepare replies to your mail as drafts, which you send yourself, and move your mail between your folders, archive it or put it in the trash",
				"fr": "préparer des réponses à tes mails en brouillons, que tu envoies toi-même, et déplacer tes mails d'un dossier à l'autre, les archiver ou les mettre à la corbeille"
			}
		}
	}
}
```

A domain the document does not name in the owner's language goes by its name in the deployment's language, since a product's name rarely changes with the language, or else by its id, and what a level covers shows in the owner's language only, or not at all. The question stays the harness's own text, which the chat renders as Markdown: an entry whose words hold a markup character (``\ ` * _ ~ [ ] < > &``), anything that looks like a link, an address or a domain name, or a break of any kind is ignored with a warning, and so is an entry of any other shape, a key or a language code the harness does not know included, while the rest of the catalog loads; what goes in is escaped once more. The words are read with the catalog, at each refresh, so a new application needs no release of the harness.

The question asks for an answer in words, and carries no buttons: Twake Chat sends a reaction in the clear even in an encrypted room, so a tap on a button could never answer. The owner answers with an exact yes or no as their next message after the question, in any language the harness speaks, or with a bare ✅ or ❌ on it from a client that encrypts its reactions; anything else they write is an ordinary message, after which only such a reaction, or an answer through the API, answers. The matrix role reads the answer itself, never the model, and only from an event that reached the assistant encrypted, sent by the owner: a reaction or a message written in the owner's name on the server, which cannot encrypt for the room, answers nothing, and an answer delivered twice answers once. A no drops the call and erases what it would have sent; the harness says so itself, without the model. A yes approves the call at once and queues a `resume` job with the owner's turns. The job grants the consent when the question asked for one, runs the call exactly as it was frozen, under the correlation id of the turn that froze it, records it in the session as the assistant's call followed by its result, erases what it sent from the waiting call, and lets the model go on, unless the call waits for its owner again, which ends the turn on the harness's new question; a resumed turn is admitted like any other.

Besides each application, an owner gives the platform's token broker, once, the permission for their assistant to act for them at all. When the broker has none, or the one it had expired, the gateway answers a contract call with the broker's 401, an RFC 9457 problem whose `code` is `delegation_missing` or `delegation_expired`. The call then waits for its owner, for the reason `delegation`, and the turn ends on the harness's own request, whatever the model would have said: what the call was about to do, in the application named as for a first use, why it waits, where to give that permission, and how to answer, as any question of the harness asks. The only link it shows is the broker's consent link the deployment sets in `BROKER_CONSENT_URL` (checked at start), never the `consent_url` of the answer, which a contract could write as well; without that setting, the request says why and offers to try again, with no link. The model's view of the call records that it waited for that permission. The owner's yes runs the frozen call again, once, and grants no consent; a call the broker refuses again ends the resumed turn on a new request. The organization agent, which acts for no user, reads that refusal as data.

A question expires after `CONSENT_REQUEST_LIFETIME_MS`, a day by default, and a newer question in the same room supersedes it: an answer to either runs nothing, and only the first answer gets a notice; what the call would have sent is erased. Every hour, the worker role expires the questions nobody answered.

The owner asks their assistant what it may access, and the model answers from `consents_list`: each application and level the owner allowed, how and when, and the reading of the assistant's own feed of events, built into the harness. The owner tells it to stop using an application, or only to stop writing there, and the model calls `consents_withdraw` with the application and, for writing alone, the `write` level: the next call there asks the owner again, on every replica at once, since every check reads the database. A name the catalog does not offer is refused, with the applications it does offer, unless the owner had allowed it before the catalog dropped it. The withdrawal also closes the questions still open there and the calls the owner allowed that have not run yet, as a newer question closes an older one: an answer to such a question gets the notice, and nothing runs there after the withdrawal. No tool grants a consent; only the owner's own answer does. Withdrawing takes the `consents.withdraw_own` right, which every principal that can chat holds and a turn an event started never does: an event's text cannot make the assistant withdraw anything. In the owner's own turns, text the assistant reads, a mail for instance, could still lead it to withdraw a consent, which only makes it ask again. The organization agent, which holds no consent, neither lists nor withdraws one.

A high-risk write, one that sends words to other people in the owner's name, shares or publishes, deletes for good, or trains what other users share, waits for its owner every time, whatever they allowed, and runs only once they confirmed that very call. One request asks about every reason a call waits for: the first high-risk write in an application asks once, and its yes both allows writing there and confirms that call, whereas a yes that only confirms a call allows nothing more; should its owner take writing back before they confirm, the call waits again, asking for both, and the request they answered is closed as superseded, as it is when the broker refuses a call again.

A turn an event started reads as any turn does, its first read of an application asking as it would in a conversation, but every write it prepares waits for its owner, whatever they allowed, since what arrived was written by someone else: what the model wrote alongside the call, quoted in the request, carries the event's context. The owner's yes runs that very call and nothing more. The turn it resumes is still the event's, as if it had never stopped: any other write it prepares asks again, and it never changes how the assistant speaks to its owner, keeps a note or a skill proposal, or withdraws a consent, which only the owner's own turns do. A write that is also the first in its application asks both in one request, whose yes also allows writing there.

A request about a first use, a high-risk write or a write that a turn an event started prepared shows, in order: what the model wrote alongside the call, quoted under the harness's label ("Your assistant wrote:"), at most 2,000 characters of it; the harness's question, which names the application and, for a first use, says what the level covers there; the call itself, whole, as the model wrote it, in a code block, or, for a write that offers a preview, what its application says it would do, in its place, quoted under the harness's label ("Twake Mail describes it as:"); and how to answer. A call the model wrote without arguments, such as listing the mailboxes, never shows its owner an empty `{}`: unless a summary stands in its place, a first use shows no call, its question asking only whether its owner allows it, since it already says what the level covers there, and a question about that very call, a high-risk write's or an event turn's, shows the tool it calls instead, as the harness names it. The harness lays the message out itself, as plain text and as HTML. What the model wrote renders its Markdown, held whole in the quote under the harness's label, every tag of it closed within it, but with nothing that acts, since Twake Chat opens a link on a touch without asking and a received mail may have phrased those words: none of its HTML, a link as its text alone, an address or an e-mail address as text, an image as its description, which no client then fetches from another server, and a heading as a paragraph. It shows as its lines of text should its rendering take more of the event than those escaped lines could, 12,000 bytes, and the plain text quotes it line by line. The question renders from the harness's own Markdown, and the call or its application's summary, which may hold what a third party wrote, shows as code: nothing the model or a third party wrote passes for the harness's words. An owner is never asked about a call they cannot see whole: a call, or a summary, that would take more than 16 KiB of the event that carries the request, as plain text and as HTML together, escaped as the event's JSON holds them, waits for nothing, and the model reads that it is too large to confirm, so that it may make it smaller. With the model's words, 12,000 bytes at most in each, the largest request stays under 60 KiB once encrypted, well within the 64 KiB a Matrix event may take. A request travels in its parts, the question apart from the call, and the API answers a turn with its plain text. The conversation keeps the request for the model's later turns as its owner read it, with the call as the model wrote it in place of what an application said of it: that is the application's data, which may hold what a third party wrote, possibly from an application the owner never let the assistant read, and only the owner reads it, in the request itself, which the harness stores nowhere else. A call without arguments is kept as its owner read it, without an empty call, since the model's own call, just before the request in the conversation, already says what would run; but where its owner read a summary, the conversation shows the call as the model wrote it, `{}`, as it does for any call with a preview.

When the application can tell what a write would affect, such as the recipients a mail would reach or the item it would delete, its owner sees that rather than the call the model wrote. Before it asks about a write whose operation declares `x-twake-preview: true`, the harness calls the contract as the call would go, same method, path, query and body, in the owner's name and under the correlation id of the turn, with `x-twake-preview: true` and the owner's language in `accept-language`. The contract answers what the call would do, and does nothing: a `200` that carries `x-twake-preview: true` back in its own headers, whose JSON body holds a `summary`, plain text for the owner, on several lines if need be, without any control or format character but line feeds and tabs, and a `digest`, an opaque token of 1 to 256 letters, digits or `+ / = . _ : -` that covers what the call acts on:

```json
{
	"summary": "To: Paul Martin <paul@example.com> and the 3 members of finance\nSubject: Q4 budget",
	"digest": "sha256:4f1c2e9a"
}
```

The request shows the summary in the call's place, as data, as it would show the call. Only a write that declares the preview is ever called so, and only to ask its owner: a contract that never promised a preview would take that call for the action itself, and a read before its owner allowed it would read their data. The harness keeps the digest with the frozen call, and the call its owner allowed carries it in `x-twake-preview-digest`, never `x-twake-preview`. A contract that finds what the call acts on changed since answers `409` and does nothing: the harness then tells the owner itself that the action was not done, without the model, which reads in the conversation the call, the contract's answer and that notice. The digest is erased with what the call would send once the call is decided, and neither it nor the summary is ever logged.

Any other answer to a preview asks the owner nothing. A preview the broker refuses for want of the owner's permission asks for that permission, as a refused call does, and the call is previewed once it may be. Any other success is taken for the call itself, done, since a contract that ignores the header answers that way: the turn ends on the harness's own notice that the application did the action without waiting for the owner's yes, the model reads that the call was made, with the status of the answer and never its body, which may hold a summary meant for the owner, the operator reads an error, and the replica stops previewing that contract until its catalog loads again, so that no other preview there acts. An error, which the model reads to fix the call or tell its owner, and no answer in time, after which the model reads that whether the application did anything is unknown, leave the contract previewed, and the operator reads a warning that says what was wrong, never what the contract answered.

With their own token, and under their own rights as on the other owner routes, `chat` to read, grant and answer and `consents.withdraw_own` to withdraw, an owner manages their consents through the API, as a settings page would: `GET /v1/consents` lists them, the built-in feed included; `PUT /v1/consents/{application}/{level}` grants a level the catalog offers (201, or 200 when it was given already), and `DELETE /v1/consents/{application}/{level}` withdraws one (204, 404 when there is none, 409 for the built-in feed). A turn through `POST /v1/chat` that stops on the harness's question answers with the whole request, as the room shows it, and returns the call it froze as `pending_call` beside it, and a direct call through `POST /v1/tool` answers 202 with that call instead of running; a pending call shows the question alone. `GET /v1/pending-calls` lists what waits for the owner's answer, asked in their room (`room`), in a turn through the API's chat (`api_chat`) or by a direct call through its tool route (`api_tool`): its id, application, level, reasons, the harness's question with what the application and level cover there, and when it expires, never what the call would send nor the model's words alongside it. `POST /v1/pending-calls/{id}/approve` answers yes: a call asked in the room resumes there as after a ✅ (202), a turn through the API goes on and answers as `POST /v1/chat` does, admitted like any turn, the call still waiting if the turn is refused, and a direct tool call runs and answers as `POST /v1/tool` does, under the owner's rights at that moment; the consent a yes to a first use grants is recorded as given through the API. `POST /v1/pending-calls/{id}/refuse` answers no, and in the room the harness says so as after a ❌. An answer through the API is recorded under an id of its own, `api:` and the request's id, as one in the room is under its event's, so that the first answer wins, in the room or through the API, however close they come: a later one through the API gets a 409 with the call's state, and a later one in the room changes nothing. A yes through the API runs a call of a turn through the API, or of a direct tool call, at once, with no job behind it: should its replica die before the call runs, the owner's next yes runs it once the lease a replica holds a job for, fifteen minutes, has passed, and gets a 409 before. Another owner's consents and calls stay out of reach under row-level security: the routes answer 404.

Each role counts on its own `/metrics` what it does of consent, by application (`domain`), `level` and `reason`, never by owner, room or argument; a call that waits for several reasons counts once, under all of them joined by `+`. The api role counts the calls it freezes, `harness_consent_requests_total`, and the calls it runs once their owner allowed them, `harness_consent_replays_total`, whose `outcome` is `ok` when the application answered with a success and `failed` otherwise. The matrix role counts the owners' answers in the chat, and the api role those given through it, `harness_consent_answers_total`, by `answer` (`yes` or `no`), `via` (`reaction`, `words` or `api`) and `outcome`: `decided`, or `expired` or `superseded` for an answer that came too late and ran nothing. It also counts the questions a newer one superseded, `harness_consent_supersessions_total`, which the api role counts too for the questions and calls a withdrawal closes, and those an answer found past their lifetime, `harness_consent_expiries_total`, in which the api role counts those it finds too, and the worker role the questions its hourly pass expires. A counter shows once it counted, and, like every counter of `/metrics`, is its replica's own: a dashboard sums it over the replicas of the role. A replay or a frozen call retried after a failed commit may be counted twice, by the replica that retries it.
